# Структура административной панели ИВС-СЕТИ

Требования из переписки: сотрудники сами редактируют контент без программиста; по возможности меняют структуру страниц (сборка из готовых блоков); система не должна привязывать компанию к одному разработчику.

## Роли и доступ

| Роль | Что может |
|---|---|
| Администратор | Всё: пользователи, настройки, структура, контент |
| Редактор | Контент: новости, мероприятия, проекты, страницы, медиа. Без доступа к настройкам и пользователям |

Вход: логин/пароль, сброс пароля по почте, сессии с авто-выходом. Двухфакторка — опционально на этапе внедрения.

## Разделы админки

```
/admin
├── Дашборд                Сводка: последние изменения, черновики, базовая статистика посещений
├── Контент
│   ├── Новости            CRUD: заголовок, дата, анонс, текст, обложка, публикация/черновик
│   ├── Мероприятия        CRUD + признак внешнего материала (перенос с iteventpermkrai.tilda.ws)
│   ├── Проекты            CRUD кейсов: заказчик, направление, задача/решение/результат, галерея, теги, «избранное на главную»
│   ├── Услуги             Редактирование описаний 8 направлений и ~30 подуслуг (структура разделов фиксирована в коде, тексты — в админке)
│   ├── Партнёры           CRUD: логотип, название, описание, ссылка, порядок вывода, статус партнёрства
│   ├── Отзывы             CRUD: автор, компания, текст/скан, дата
│   ├── Вакансии           CRUD: должность, описание, контакты HR, активность
│   └── Лицензии           CRUD: название, файл (PDF/JPG), срок действия, порядок
├── Страницы (конструктор)
│   ├── Список страниц     Все статичные страницы: о компании, контакты, реквизиты, произвольные
│   ├── Редактор страницы  Сборка из готовых блоков перетаскиванием:
│   │                      hero, текст, карточки, цифры, галерея, список, CTA-контакты, врезка, таблица
│   └── Библиотека блоков  Предпросмотр всех доступных блоков с описанием
├── Меню                   Редактирование пунктов шапки и футера в пределах допустимого
│                          (порядок, видимость; типы меню фиксированы)
├── Медиабиблиотека        Загрузка и организация изображений/файлов: папки, превью, alt-тексты,
│                          автосжатие в WebP, ограничение по весу
├── SEO                    Шаблоны title/description по типам страниц + ручное переопределение
│                          на каждой странице, Open Graph-изображения
├── Аналитика              Встройка дашборда Яндекс.Метрики (просмотр, без редактирования),
│                          поле для ID счётчика в настройках
├── Настройки
│   ├── Общие              Название сайта, контакты в шапке/футере, реквизиты, режим обслуживания
│   ├── Пользователи       CRUD пользователей админки, роли, сброс паролей
│   ├── Интеграции         ID Яндекс.Метрики, токены внешних сервисов
│   └── Резервные копии    Экспорт контента (JSON/архив), история версий страниц
└── Журнал                 Кто, что и когда изменил (аудит действий)
```

## Ключевые принципы реализации

1. **Контент отделён от кода.** Все тексты, карточки и медиа хранятся в БД (SQLite/PostgreSQL на ВМ заказчика), а не в исходниках. Исходный код остаётся в репозитории компании на GitHub.
2. **Конструктор, а не свободная вёрстка.** Редактор собирает страницу из типовых блоков дизайн-системы — сломать вёрстку невозможно, новые блоки добавляет разработчик.
3. **Предпросмотр до публикации.** Черновик можно открыть по секретной ссылке и показать коллегам до выкладки.
4. **Версионирование.** У каждой страницы — история изменений с откатом.
5. **Простота передачи.** Админка — часть того же Next.js-проекта (отдельный маршрут), без экзотических зависимостей: любой React-разработчик среднего уровня поддержит.

## Что НЕ входит в админку (осознанно)

- Формы обратной связи и их обработка — исключены требованием заказчика (24.09).
- Интернет-магазин, корзина, личные кабинеты — вне рамок корпоративного сайта.
- Редактирование дизайн-токенов (цвета, шрифты) — зашиты в дизайн-систему, чтобы исключить развал визуала.
